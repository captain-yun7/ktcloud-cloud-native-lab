# 실습 5. 로드밸런서와 헬스 체크

**무엇을 하나요**: 사내망에 **두 번째 웹 서브넷**과 서버 `web-b`를 붙여, web을 **서로 다른 서버 자리 두 곳**(다른 랙 · 다른 전원)에 둡니다. 그 앞에 입구를 두 가지 놓습니다. 하나는 **번갈아 보내기만 하는 입구**(9091), 다른 하나는 **nginx 로드밸런서**(9090)입니다. 그다음 서버 자리 a(web)를 멈추고 세 곳(web 직접 · 9091 · 9090)을 20번씩 불러 비교합니다. 로드밸런서가 실패한 서버를 빼는 **헬스 체크**를 숫자로 보고, 쿠버네티스에서 같은 일을 하는 readinessProbe를 찾습니다. (교안 05장)

**필요한 것**: 실습 4까지(줄임말 · `vpc-up.sh`). 이미지 `nginx:1.29-alpine`(Docker 과목에서 받음). 사내망은 1단계에서 다시 만듭니다.

## 1단계. 두 서버 자리에 web 두기

```bash
cd ~/ktcloud-cloud-native-lab && git pull && cd lab/network
sudo bash vpc-up.sh --az2
alias web="sudo ip netns exec web" webb="sudo ip netns exec web-b" rt="sudo ip netns exec rt"
curl -s 10.0.1.10; curl -s 10.0.3.10
rt ip route
```

**이 명령은**: 2줄 = 실습 3이 끝난 사내망에 **두 번째 웹 서브넷**(`10.0.3.0/24`, 서버 `web-b` `10.0.3.10` — 다른 랙 자리)까지 붙여 만듦. 3줄 = 줄임말(`webb` = web-b 안에서). 4줄 = 두 서버를 VM에서 부름. 5줄 = 라우터의 표.

**이렇게 나오면 성공**

```
라우팅·NAT·서버 + 두 번째 AZ(web-b)까지 준비 완료:
web-b (id: 6)
db (id: 4)
web (id: 3)
rt (id: 0)
web 10.0.1.10
web-b 10.0.3.10
default via 10.0.255.1 dev rt-igw
10.0.1.0/24 dev rt-web proto kernel scope link src 10.0.1.1
10.0.2.0/24 dev rt-db proto kernel scope link src 10.0.2.1
10.0.3.0/24 dev rt-webb proto kernel scope link src 10.0.3.1
10.0.255.0/30 dev rt-igw proto kernel scope link src 10.0.255.2
```

```
        ┌──────────── 사내망 10.0.0.0/16 ─────────┐
        │  자리 a                 자리 b           │
        │  10.0.1.0/24 web        10.0.3.0/24 web-b│
        │  10.0.2.0/24 db                          │
        └──────────────────────────────────────────┘
```

- 라우터에 `10.0.3.0/24` 줄이 늘었습니다. 두 번째 자리의 서버는 자기 웹 서브넷을 따로 받았습니다(이 실습에서는 자리마다 서브넷 하나)
- 첫 줄의 "두 번째 AZ"는 스크립트가 찍는 글자 그대로입니다. 이 문서의 "두 번째 서버 자리"와 같은 뜻입니다
- 서브넷을 직접 붙이는 순서는 [부록 A1](../부록/A1-두-번째-서브넷-수동-구성.md)에 있습니다(`--az2`가 그 줄들을 대신 넣음)

## 2단계. 번갈아 보내기만 하는 입구 — 9091

```bash
VM=$(hostname -I | cut -d' ' -f1)
sudo iptables -t nat -A OUTPUT -d $VM -p tcp --dport 9091 -m statistic --mode nth --every 2 --packet 0 -j DNAT --to-destination 10.0.1.10:80
sudo iptables -t nat -A OUTPUT -d $VM -p tcp --dport 9091 -j DNAT --to-destination 10.0.3.10:80
for i in 1 2 3 4; do curl -s $VM:9091; done
```

**이 명령은**: 1줄 = VM 주소를 변수 `VM`에. 2줄 = VM의 9091로 온 연결 중 **2번에 한 번**은 web으로. 3줄 = 나머지는 web-b로. 4줄 = 4번 불러 보기.

**이렇게 나오면 성공**

```
web 10.0.1.10
web-b 10.0.3.10
web 10.0.1.10
web-b 10.0.3.10
```

- 실습 3 6단계의 포트 포워딩(DNAT — 받는 주소 바꾸기)을 두 줄로 나눈 것입니다. 요청을 **번갈아 보내기만** 하고, 상대가 살아 있는지는 보지 않습니다

<details><summary><b>이렇게 나오면?</b> — 자주 나는 오류와 해결 (눌러서 펼치기)</summary>

| 화면 | 원인 | 해결 |
|---|---|---|
| 아무것도 안 나옴 | `VM` 변수가 비어 있음 | 1줄 다시, `echo $VM`이 `10.10.1.N` |
| `web-b`만 나옴 | 2줄을 빠뜨림 | `sudo iptables -t nat -S OUTPUT \| grep 9091`에 두 줄 |

</details>

## 3단계. 로드밸런서 띄우기 — 9090

```bash
cat lb/nginx.conf
docker run -d --name lab-lb --network host -v $PWD/lb/nginx.conf:/etc/nginx/nginx.conf:ro nginx:1.29-alpine
for i in 1 2 3 4; do curl -s localhost:9090; done
```

**이 명령은**: 1줄 = 로드밸런서 설정 파일 읽기. 2줄 = nginx 컨테이너 `lab-lb`를 VM 네트워크 그대로(`--network host`) 띄우고 설정을 넣음 → VM의 9090번이 로드밸런서. 3줄 = 4번 불러 보기.

**설정 파일**(가운데 부분)

```nginx
upstream web {
  server 10.0.1.10:80 max_fails=1 fail_timeout=10s;   # AZ-a
  server 10.0.3.10:80 max_fails=1 fail_timeout=10s;   # AZ-b
}
server {
  listen 9090;
  location / { proxy_pass http://web; proxy_connect_timeout 1s; }
}
```

| 줄 | 뜻 |
|---|---|
| `upstream web { … }` | 요청을 받을 서버 목록(두 자리 — 파일 주석의 `AZ-a`·`AZ-b`가 자리 a·b) |
| `max_fails=1 fail_timeout=10s` | 한 번 실패하면 10초 동안 그 서버를 목록에서 뺌 = **헬스 체크** |
| `listen 9090` | 로드밸런서가 사용자를 받는 포트 |
| `proxy_pass http://web` | 받은 요청을 목록의 서버로 넘김 |
| `proxy_connect_timeout 1s` | 1초 안에 연결 안 되면 실패로 보고 다른 서버로 |

**이렇게 나오면 성공** (2줄은 컨테이너 ID — 사람마다 다름)

```
6a4480ed0c8b…
web 10.0.1.10
web-b 10.0.3.10
web 10.0.1.10
web-b 10.0.3.10
```

| 화면 | 원인 | 해결 |
|---|---|---|
| `Conflict. The container name "/lab-lb" is already in use` | 이미 띄움 | `docker rm -f lab-lb` 후 다시 |
| 아무것도 안 나옴 | 컨테이너가 바로 꺼짐 | `docker logs lab-lb` 첫 오류 줄. `lab/network` 폴더에서 실행했는지(`$PWD`) |
| `Unable to find image 'nginx:1.29-alpine' locally` 후 받기 시작 | Docker 과목에서 받은 이미지를 지웠음 | 받을 때까지 기다림 |

</details>

## 4단계. 서버 자리 a 장애 — 세 곳을 20번씩

```bash
sudo ip netns pids web | xargs -r sudo kill
ok(){ n=0; for i in $(seq 1 20); do [ "$(curl -s -m 2 -o /dev/null -w %{http_code} $1)" = 200 ] && n=$((n+1)); done; echo "$n/20"; }
ok 10.0.1.10
ok $VM:9091
ok localhost:9090
docker logs lab-lb 2>&1 | grep -m1 "connect() failed"
```

**이 명령은**: 1줄 = web 안에서 도는 프로그램(웹 서버)을 모두 끔 = **서버 자리 a 장애**. 2줄 = `ok` = 주소를 20번 불러 200(성공)이 몇 번인지 세는 작은 함수. 3~5줄 = web 직접 · 번갈아 입구 · 로드밸런서. 6줄 = nginx 로그에서 실패 기록 한 줄.

**이렇게 나오면 성공**

```
0/20
10/20
20/20
2026/10/22 13:36:19 [error] 30#30: *9 connect() failed (111: Connection refused) while connecting to upstream, client: 127.0.0.1, server: , request: "GET / HTTP/1.1", upstream: "http://10.0.1.10:80/", host: "localhost:9090"
```

| 자리 a 장애 중 | 20번 중 성공 | 왜 |
|---|---|---|
| web 직접 (서버 한 대뿐) | `0/20` | 다른 곳이 없음 |
| 9091 번갈아 보내기 | 약 `10/20` | 멈춘 web으로도 절반을 계속 보냄 |
| 9090 로드밸런서 | `20/20` | 실패하면 web-b로 다시 보내고, web을 10초 동안 뺌 |

- 서버를 두 자리에 두는 것(9091)만으로는 요청 절반이 오류를 받습니다. **응답하는 서버로만 보내는 기능 = 헬스 체크**가 있어야 `20/20`
- 로그의 `connect() failed (111: Connection refused)` = nginx가 web에 보냈다가 거절당한 기록. 그 요청은 web-b가 답했으므로 사용자는 성공만 봅니다

<details><summary><b>이렇게 나오면?</b> — 자주 나는 오류와 해결 (눌러서 펼치기)</summary>

| 화면 | 원인 | 해결 |
|---|---|---|
| `ok 10.0.1.10`이 `20/20` | web이 안 꺼짐 | 1줄 다시, `sudo ip netns pids web`이 빈 출력인지 |
| 9091이 `0/20` | `VM` 변수가 비어 있음(새 터미널) | `VM=$(hostname -I \| cut -d' ' -f1)` 다시 |
| 9091이 `9/20`·`11/20` | 세는 시점에 따라 조금 다름 | 정상 |
| `ok: command not found` | 새 터미널 | 2줄 다시 |

</details>

## 5단계. 서버 자리 a 복구

```bash
web sh -c 'cd /tmp/vpc-web && nohup python3 -m http.server 80 >/dev/null 2>&1 &'
sleep 12; for i in 1 2 3 4 5 6; do curl -s localhost:9090; done
```

**이 명령은**: 1줄 = web 서버를 다시 켬(`/tmp/vpc-web`은 `vpc-up.sh`가 만든 폴더). 2줄 = 12초 기다린 뒤(빠졌던 10초가 지나도록) 6번 부르기.

**이렇게 나오면 성공**: `web 10.0.1.10`이 다시 섞여 나옴

```
web-b 10.0.3.10
web-b 10.0.3.10
web 10.0.1.10
web-b 10.0.3.10
web 10.0.1.10
web-b 10.0.3.10
```

- nginx는 빼 둔 시간(10초)이 지나면 web에 다시 보내 보고, 성공하면 목록에 돌려놓습니다. 처음 몇 번이 web-b만인 것은 그 시점 차이입니다

<details><summary><b>이렇게 나오면?</b> — 자주 나는 오류와 해결 (눌러서 펼치기)</summary>

| 화면 | 원인 | 해결 |
|---|---|---|
| 6번 모두 web-b | 10초가 안 지났거나 web 서버가 안 켜짐 | `curl -s 10.0.1.10` 먼저. 되면 몇 초 뒤 2줄 다시 |
| `can't cd to /tmp/vpc-web` 류 | 1단계를 `--az2` 없이 함 | 1단계부터 다시 |

</details>

## 6단계. 쿠버네티스에서는 — readinessProbe

```bash
kubectl -n shop get endpointslices -l kubernetes.io/service-name=frontend
kubectl -n shop get deploy frontend -o jsonpath='{.spec.template.spec.containers[0].readinessProbe}'; echo
```

**이 명령은**: 1줄 = Online Boutique frontend Service가 요청을 보내는 대상 목록(EndpointSlice). 2줄 = frontend 파드의 readinessProbe 설정.

**이렇게 나오면 성공** (주소·이름 뒤 글자는 달라도 됨)

```
NAME             ADDRESSTYPE   PORTS   ENDPOINTS     AGE
frontend-bkrnn   IPv4          8080    10.244.2.28   2d7h
{"failureThreshold":3,"httpGet":{"httpHeaders":[{"name":"Cookie","value":"shop_session-id=x-readiness-probe"}],"path":"/_healthz","port":8080,"scheme":"HTTP"},"initialDelaySeconds":10,"periodSeconds":10,"successThreshold":1,"timeoutSeconds":1}
```

| 로드밸런서(3단계 nginx) | 쿠버네티스 |
|---|---|
| `upstream web { … }` 서버 목록 | EndpointSlice의 `ENDPOINTS` |
| `max_fails=1 fail_timeout=10s`(실패하면 뺌, 수동) | readinessProbe: 10초마다 `/_healthz`를 찔러 봄(`periodSeconds: 10`), 3번 실패하면 뺌(`failureThreshold: 3`) — 능동 |
| 9090 입구 | Service(`frontend`) |

- 준비 안 된 파드는 `ENDPOINTS`에서 빠지고, Service는 그 파드로 보내지 않습니다 — 로드밸런서의 헬스 체크와 같은 일

<details><summary><b>이렇게 나오면?</b> — 자주 나는 오류와 해결 (눌러서 펼치기)</summary>

| 화면 | 원인 | 해결 |
|---|---|---|
| `No resources found in shop namespace.` | shop을 지웠음 | 결과 표만 보고, Kubernetes 실습 9의 probe를 떠올림 |
| 2줄이 빈 출력 | probe가 없는 앱 | 정상(그 앱은 헬스 체크 없이 늘 대상). 표만 봄 |

</details>

## 끝났는지 확인

- ☐ `rt ip route`에 `10.0.3.0/24`, web·web-b 둘 다 응답
- ☐ 9091·9090 둘 다 번갈아 응답
- ☐ 자리 a 장애 중 `0/20` · 약 `10/20` · `20/20`
- ☐ 복구 후 9090에서 web이 다시 섞여 나옴
- ☐ frontend의 EndpointSlice와 readinessProbe(`/_healthz`, 10초)를 찾음

## 정리

```bash
docker rm -f lab-lb; sudo bash ~/ktcloud-cloud-native-lab/lab/network/vpc-down.sh
```

**이렇게 나오면 성공**: `lab-lb`, `정리 완료`. 9091 규칙도 함께 지워집니다.

### 클라우드에서는

- 이 실습의 서버 자리 a/b(다른 랙 · 다른 전원)를 AWS에서는 **가용 영역(AZ)** 이라고 부릅니다. 서브넷 하나는 가용 영역 하나에 속합니다
- 9090 nginx 같은 로드밸런서는 **ELB(ALB · NLB)**, 헬스 체크는 **대상 그룹 헬스 체크**(능동 — 미리 찔러 봄)입니다
- 이름 맞추기는 교안 06장 대응표에서 한 번에 봅니다
