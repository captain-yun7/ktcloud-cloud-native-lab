# 부록 B2. 네트워크 최적화 — 거리와 비용

> 부록 — 본편(D-30) 밖, 클라우드(AWS) 이름으로 더 보고 싶을 때 보는 문서입니다.

**무엇을 하나요**: 네트워크를 "빠르고 싸게" 만드는 두 가지 기준, **거리(지연)** 와 **지나가는 부품(비용)** 을 숫자로 봅니다. VM에서 AWS 리전 다섯 곳(서울 · 도쿄 · 미국 서부 · 미국 동부 · 유럽)까지 연결 시간을 재고, VPC 안 · 서버 · 인터넷 가까운 곳의 왕복 시간과 나란히 놓습니다. 그다음 실습 3의 NAT를 지나간 바이트를 세어, 클라우드에서 NAT 게이트웨이 요금이 왜 붙는지와 **VPC 엔드포인트**로 줄이는 이유를 봅니다. 마지막에 트래픽마다 요금이 붙는 곳을 표로 정리합니다. (교안 부록 B)

**필요한 것**: 실습 4까지(줄임말 · `vpc-up.sh`). VPC는 2단계에서 다시 만듭니다.

> **바로 가기** · [1. 리전까지의 거리](#1단계-리전까지의-거리) · [2. 가까운 곳의 왕복 시간](#2단계-가까운-곳의-왕복-시간) · [3. NAT를 지나간 양 세기](#3단계-nat를-지나간-양-세기) · [4. 요금이 붙는 길 표 채우기](#4단계-요금이-붙는-길-표-채우기) · [끝났는지 확인](#끝났는지-확인) · [정리](#정리) · [확인 문제](#확인-문제)

## 1단계. 리전까지의 거리

```bash
for r in ap-northeast-2 ap-northeast-1 us-west-2 us-east-1 eu-west-1; do curl -s -o /dev/null -m 5 -w "$r  연결 %{time_connect}  TLS %{time_appconnect}  %{http_code}\n" https://ec2.$r.amazonaws.com/ping; done
```

**이 명령은**: AWS 리전 다섯 곳의 EC2 서비스 주소(`/ping` = 살아 있나 확인용)에 차례로 HTTPS 접속해, **연결(TCP)** 이 끝난 시간과 **TLS**가 끝난 시간을 찍음(실습 1 2단계의 그 칸).

**이렇게 나오면 성공** (시간은 회선·때에 따라 다름)

```
ap-northeast-2  연결 0.040827  TLS 0.071808  200
ap-northeast-1  연결 0.070298  TLS 0.139918  200
us-west-2  연결 0.176057  TLS 0.462425  200
us-east-1  연결 0.223285  TLS 0.600685  200
eu-west-1  연결 0.295975  TLS 0.814870  200
```

| 리전 | 어디 | 연결(왕복 한 번) | TLS까지 |
|---|---|---|---|
| `ap-northeast-2` | 서울 | 0.041초 | 0.072초 |
| `ap-northeast-1` | 도쿄 | 0.070초 | 0.140초 |
| `us-west-2` | 미국 서부(오리건) | 0.176초 | 0.462초 |
| `us-east-1` | 미국 동부(버지니아) | 0.223초 | 0.601초 |
| `eu-west-1` | 유럽(아일랜드) | 0.296초 | 0.815초 |

- 멀수록 연결이 길고, **TLS까지는 차이가 더 벌어집니다**(왕복을 여러 번 하므로). 서울 대 미국 동부: 연결 약 5배, TLS까지 약 8배
- 사용자가 한국에 있으면 서울 리전 — 이것이 **리전 선택**의 첫 기준입니다

| 화면 | 원인 | 해결 |
|---|---|---|
| 한 줄이 `연결 0.000000 … 000` | 5초 안에 연결 못 함 | 한 번 더. 계속이면 그 줄만 빼고 비교 |
| 숫자가 문서보다 두 배쯤 | 회선이 붐빔 | 두세 번 돌려 작은 값을 봄. 리전 사이 **순서**가 같으면 됨 |

</details>

## 2단계. 가까운 곳의 왕복 시간

```bash
cd ~/ktcloud-cloud-native-lab/lab/network && sudo bash vpc-up.sh --routed
alias web="sudo ip netns exec web" db="sudo ip netns exec db" rt="sudo ip netns exec rt"
web ping -c3 -q 10.0.2.10 | tail -1
ping -c3 -q 10.10.0.1 | tail -1
ping -c3 -q 1.1.1.1 | tail -1
```

**이 명령은**: 1·2줄 = 실습 3이 끝난 VPC를 다시 만들고 줄임말. 3줄 = VPC 안 web → db. 4줄 = VM → 서버(`10.10.0.1`, 같은 서버실). 5줄 = VM → 인터넷의 가까운 곳(`1.1.1.1`). 각각 3번 왕복의 평균만(`-q` + 마지막 줄).

**이렇게 나오면 성공**

```
rtt min/avg/max/mdev = 0.051/0.055/0.059/0.003 ms
rtt min/avg/max/mdev = 0.140/0.190/0.225/0.036 ms
rtt min/avg/max/mdev = 2.175/2.281/2.365/0.079 ms
```

| 어디까지 | 왕복(avg) | 비슷한 클라우드 상황 |
|---|---|---|
| VPC 안 web → db | 0.055ms | 같은 VPC · 같은 호스트 |
| VM → 서버 `10.10.0.1` | 0.19ms | 같은 데이터센터 안 |
| VM → `1.1.1.1` | 2.3ms | 인터넷의 가까운 곳 |
| VM → 서울 리전(1단계) | 약 41ms | 회선을 지나 리전까지 |
| VM → 미국 동부(1단계) | 약 223ms | 다른 대륙 |

- 단위가 다릅니다: 1단계는 **초**, 여기는 **ms**(1/1000초). VPC 안은 미국 동부보다 약 4,000배 가깝습니다
- 자주 대화하는 서버끼리(web ↔ db)는 **가까이** 둡니다 — 같은 VPC, 되도록 같은 AZ

<details><summary><b>이렇게 나오면?</b> — 자주 나는 오류와 해결 (눌러서 펼치기)</summary>

| 화면 | 원인 | 해결 |
|---|---|---|
| 3줄이 빈 출력 | VPC가 없음 | 1줄 다시(`vpc-up.sh --routed`) |
| `1.1.1.1`이 `100% packet loss` | 망이 ping을 막음 | 이 줄은 건너뜀 |

</details>

## 3단계. NAT를 지나간 양 세기

```bash
rt ip -s -h link show rt-igw | sed -n 3,4p
db curl -s -o /dev/null -w "%{size_download}바이트 %{http_code}\n" "https://speed.cloudflare.com/__down?bytes=10000000"
rt ip -s -h link show rt-igw | sed -n 3,4p
web curl -s -o /dev/null -w "%{size_download}바이트\n" 10.0.2.10:5432
rt ip -s -h link show rt-igw | sed -n 3,4p
```

**이 명령은**: `rt-igw` = 라우터의 **바깥쪽 인터페이스**(VPC → VM의 NAT → 인터넷). 1줄 = 그 인터페이스로 **들어온** 양(RX). 2줄 = 프라이빗 서브넷의 db가 인터넷에서 10MB를 받음. 3줄 = 다시 셈. 4줄 = VPC 안 web → db 접속. 5줄 = 다시 셈.

**이렇게 나오면 성공** (처음 숫자는 달라도 됨)

```
    RX:  bytes packets errors dropped  missed   mcast
           746       7      0       0       0       0
10000000바이트 200
    RX:  bytes packets errors dropped  missed   mcast
         10.3M   3.82k      0       0       0       0
13바이트
    RX:  bytes packets errors dropped  missed   mcast
         10.3M   3.82k      0       0       0       0
```

- db가 받은 10MB가 **모두 NAT 쪽 인터페이스를 지나**왔습니다(746바이트 → 10.3M). 클라우드에서는 이 양이 **NAT 게이트웨이 처리량 = 요금**입니다
- VPC 안 web → db는 이 선을 **지나지 않습니다**(그대로 10.3M)
- 프라이빗 서버가 S3 같은 AWS 서비스에서 받는 것도 원래는 이 길(NAT)로 옵니다. **VPC 엔드포인트**를 두면 VPC 안의 지름길로 와서 NAT를 지나지 않습니다

<details><summary><b>이렇게 나오면?</b> — 자주 나는 오류와 해결 (눌러서 펼치기)</summary>

| 화면 | 원인 | 해결 |
|---|---|---|
| `0바이트 000` | 2단계 VPC가 없거나 NAT 없음 | 2단계 1줄(`vpc-up.sh --routed`) 다시 |
| `0바이트 000`이 계속 | 그 주소가 막힘 | `db curl -s -o /dev/null -w "%{size_download}\n" https://example.com`으로 바꿔 작은 양이라도 늘어나는지 |
| RX 숫자가 `10.0M`처럼 조금 다름 | 단위를 사람이 읽기 쉽게 줄여 보여 줌(`-h`) | 정상 |

</details>

## 4단계. 요금이 붙는 길 표 채우기

명령 없이 표를 채웁니다. 교안 부록 B의 그림을 보고, 각 트래픽이 **지나는 부품**과 **줄이는 방법**을 적습니다.

| 트래픽 | 지나는 부품 (NAT · AZ 경계 · 인터넷 · 엔드포인트) | 줄이는 방법 |
|---|---|---|
| ① 프라이빗 서브넷의 앱 서버가 S3에서 이미지를 받음 | | |
| ② AZ-a의 앱 서버가 AZ-b의 DB를 부름 | | |
| ③ AZ-a의 앱 서버가 같은 AZ-a의 캐시를 부름 | | |
| ④ ALB가 사용자(인터넷)에게 응답을 보냄 | | |
| ⑤ EKS 노드(프라이빗)가 ECR에서 컨테이너 이미지를 받음 | | |

**이렇게 나오면 성공**: 다섯 줄 모두 "지나는 부품"이 적힘. 요금 금액은 적지 않습니다(리전·시기마다 다름).

## 끝났는지 확인

- ☐ 리전 다섯 곳의 연결·TLS 시간을 재고, 멀수록 TLS 차이가 더 커지는 것을 봄
- ☐ VPC 안 · 서버 · 인터넷 가까운 곳의 왕복(ms)을 표에 놓음
- ☐ db가 10MB를 받을 때 `rt-igw` RX가 10MB 늘고, web → db는 그대로
- ☐ 요금 표 다섯 줄의 "지나는 부품"을 채움
