# 실습 6. 타임아웃 · 재시도 · 서킷 브레이커

**무엇을 하나요**: 입구 뒤의 앱이 **느려지거나 일부가 고장 났을 때** 손님이 겪는 일을 입구 설정으로 줄입니다. 일부러 느리게·고장 나게 만들 수 있는 연습용 앱 **flaky**를 `todo.localhost:8080/flaky`에 붙이고, 먼저 아무 설정 없이 느린 응답을 끝까지 기다리고 고장 난 파드의 503을 손님이 그대로 받는 것을 봅니다. 그다음 하나씩 더합니다 — **타임아웃**(오래 기다리지 않기) · **재시도**(다른 파드로 다시 보내기) · **고장 난 파드 빼기**(연달아 실패한 파드를 잠시 쉬게 하기) · **동시 요청 한도**(넘치면 바로 거절). 서비스 메시 실습 5에서 서비스끼리 한 것을 이번에는 **바깥 손님이 들어오는 입구**에서 합니다. (교안 06장)

**필요한 것**: 실습 1의 입구 `front`. 실습 5의 PodMonitor(확인 문제 1).

## 1단계. 연습용 앱 flaky 붙이기 — 설정 없이

```bash
cd ~/apigw
nano flaky.yaml
```

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: flaky
  namespace: todo
spec:
  replicas: 2
  selector:
    matchLabels:
      app: flaky
  template:
    metadata:
      labels:
        app: flaky
    spec:
      containers:
      - name: app
        image: todo-api:v1
        command:
        - node
        - -e
        - |
          const http = require('http'), fs = require('fs');
          http.createServer((req, res) => {
            const delay = Number(new URL(req.url, 'http://x').searchParams.get('delay') || 0);
            const code = fs.existsSync('/tmp/broken') ? 503 : 200;
            setTimeout(() => {
              console.log(`${req.url} ${code}`);
              res.writeHead(code, { 'content-type': 'application/json' });
              res.end(JSON.stringify({ pod: process.env.HOSTNAME, code }) + '\n');
            }, delay);
          }).listen(3000);
        ports:
        - containerPort: 3000
---
apiVersion: v1
kind: Service
metadata:
  name: flaky
  namespace: todo
spec:
  selector:
    app: flaky
  ports:
  - name: http
    port: 3000
```

| 부분 | 뜻 |
|---|---|
| `image: todo-api:v1` · `command: node -e …` | todo-api 이미지에 든 node로, 아래 열몇 줄짜리 프로그램을 띄움(todo-api는 실행 안 함) |
| `?delay=` | 주소에 `?delay=5000`을 붙이면 5000밀리초(5초) 늦게 답함 |
| `/tmp/broken` | 파드 안에 이 파일이 있으면 그 파드는 `503`만 돌려줌(3단계에서 만듦) |
| 응답 `{"pod": …, "code": …}` | 어느 파드가 몇으로 답했는지 |
| `replicas: 2` | 파드 둘 — 하나가 고장 나도 다른 하나가 있음 |

```bash
nano flaky-route.yaml
```

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: flaky
  namespace: todo
spec:
  parentRefs:
  - name: front
    namespace: gateway
  hostnames: ["todo.localhost"]
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /flaky
    backendRefs:
    - name: flaky
      port: 3000
```

```bash
kubectl apply -f flaky.yaml -f flaky-route.yaml
kubectl -n todo rollout status deploy/flaky
for i in 1 2 3 4 5 6; do curl -s todo.localhost:8080/flaky; done
curl -s -w " %{http_code} %{time_total}\n" "todo.localhost:8080/flaky?delay=5000"
curl -s -w " %{http_code} %{time_total}\n" "todo.localhost:8080/flaky?delay=20000"
```

**이 명령은**: 앱과 경로를 만들고, 6번 불러 어느 파드가 답하는지 보고, 5초 늦게 · 20초 늦게 답하게 해서 상태 코드와 걸린 시간(초)을 봄. 마지막 줄은 15초쯤 걸립니다.

**이렇게 나오면 성공**: 파드 이름 두 개가 섞여 나옴. 5초짜리는 5초 기다려 `200`. 20초짜리는 **15초**에 `504`

```

service/flaky created
httproute.gateway.networking.k8s.io/flaky created
deployment "flaky" successfully rolled out
{"pod":"flaky-789cb8fddf-wzd6q","code":200}
{"pod":"flaky-789cb8fddf-wzd6q","code":200}
{"pod":"flaky-789cb8fddf-dvhjz","code":200}
{"pod":"flaky-789cb8fddf-wzd6q","code":200}
{"pod":"flaky-789cb8fddf-dvhjz","code":200}
{"pod":"flaky-789cb8fddf-dvhjz","code":200}
 200 5.009103
upstream request timeout 504 15.000991
```

- 아무 설정이 없어도 Envoy는 **15초**가 지나면 끊습니다(Envoy의 기본값). 손님은 그동안 기다립니다
- 파드 이름은 사람마다 다릅니다

<details><summary><b>이렇게 나오면?</b> — 자주 나는 오류와 해결 (눌러서 펼치기)</summary>

| 화면 | 원인 | 해결 |
|---|---|---|
| flaky 파드가 `CrashLoopBackOff`, 로그에 `SyntaxError` | `- |` 아래 프로그램 줄의 들여쓰기가 깨짐 | `kubectl -n todo logs deploy/flaky -c app` 첫 줄 → 위 파일과 칸 비교 후 다시 apply |
| 파드가 `ErrImageNeverPull`·`ErrImagePull` | 노드에 `todo-api:v1`이 없음 | 질문합니다(모니터링 과목에서 넣은 이미지) |
| curl이 web의 화면(HTML)이나 `404` | `flaky-route.yaml`을 apply 안 함, 또는 `value: /flaky` 오타 | `kubectl -n todo get httproute flaky` |
| 파드 이름이 하나만 나옴 | 우연(6번은 적음) | 몇 번 더 |

</details>

## 2단계. 타임아웃 — 2초까지만 기다리기

`flaky-route.yaml`의 규칙에 `timeouts`를 더합니다(`matches`와 `backendRefs` 사이, 같은 칸).

```bash
nano flaky-route.yaml
```

```yaml
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /flaky
    timeouts:
      request: 2s
    backendRefs:
    - name: flaky
      port: 3000
```

```bash
kubectl apply -f flaky-route.yaml
sleep 3
curl -s -w " %{http_code} %{time_total}\n" "todo.localhost:8080/flaky?delay=5000"
curl -s -w " %{http_code} %{time_total}\n" "todo.localhost:8080/flaky?delay=1000"
sleep 4
kubectl -n todo logs -l app=flaky -c app --tail=3
```

**이 명령은**: 2초 한도를 넣고, 5초짜리와 1초짜리를 부름. 마지막 = 5초짜리 요청을 앱이 끝까지 처리했는지 flaky 로그로 봄.

**이렇게 나오면 성공**: 5초짜리는 **2초에** `504`, 1초짜리는 `200`. 로그에는 `delay=5000 200` — 입구가 끊은 뒤에도 앱은 끝까지 일함

```
httproute.gateway.networking.k8s.io/flaky configured
upstream request timeout 504 2.001864
{"pod":"flaky-789cb8fddf-dvhjz","code":200}
 200 1.008664
...
/flaky?delay=5000 200
```

| | 한도 없음(1단계) | `timeouts.request: 2s` |
|---|---|---|
| 5초 걸리는 요청 | 5초 기다려 `200` | 2초에 `504` |
| 20초 걸리는 요청 | 15초(기본값)에 `504` | 2초에 `504` |
| 앱 | 끝까지 처리 | 끝까지 처리(손님만 먼저 놓아줌) |

<details><summary><b>이렇게 나오면?</b> — 자주 나는 오류와 해결 (눌러서 펼치기)</summary>

| 화면 | 원인 | 해결 |
|---|---|---|
| 여전히 `200 5.0…` | apply 직후, 또는 `timeouts`가 규칙 밖(칸) | 5초 뒤 다시, `cat flaky-route.yaml` |
| `error: … unknown field "timeout"` | `timeouts`의 `s`를 빠뜨림 | `timeouts:` / `request: 2s` |
| `Invalid value: "2"` | 단위 없이 숫자만 | `2s` |

</details>

## 3단계. 파드 하나를 고장 내고 재시도

**가. 고장 내기** — flaky 파드 하나 안에 `/tmp/broken` 파일을 만들어, 그 파드만 503을 돌려주게 합니다.

```bash
BAD=$(kubectl -n todo get pods -l app=flaky -o name | head -1)
echo $BAD
kubectl -n todo exec $BAD -c app -- touch /tmp/broken
for i in $(seq 1 20); do curl -s todo.localhost:8080/flaky; done | sort | uniq -c
```

**이렇게 나오면 성공**(고장이 보이는 것이 정상): 20번 중 절반쯤이 고장 난 파드의 `503`

```
pod/flaky-789cb8fddf-dvhjz
     11 {"pod":"flaky-789cb8fddf-dvhjz","code":503}
      9 {"pod":"flaky-789cb8fddf-wzd6q","code":200}
```

**나. 재시도 정책** — 같은 경로에 **BackendTrafficPolicy**를 붙입니다. 4·5단계도 이 파일에 이어 적습니다.

```bash
nano flaky-policy.yaml
```

```yaml
apiVersion: gateway.envoyproxy.io/v1alpha1
kind: BackendTrafficPolicy
metadata:
  name: flaky
  namespace: todo
spec:
  targetRefs:
  - group: gateway.networking.k8s.io
    kind: HTTPRoute
    name: flaky
  retry:
    numRetries: 2
    retryOn:
      httpStatusCodes: [503]
      triggers: ["retriable-status-codes"]
```

| 줄 | 뜻 |
|---|---|
| `targetRefs: … name: flaky` | 1단계의 HTTPRoute `flaky`에 붙임 |
| `numRetries: 2` | 실패하면 최대 2번 더 보냄(처음 1번 + 2번) |
| `httpStatusCodes: [503]` · `triggers: ["retriable-status-codes"]` | 뒤쪽이 **503을 돌려주면** 다시 보냄 |

```bash
kubectl apply -f flaky-policy.yaml
kubectl -n todo get backendtrafficpolicy flaky -o jsonpath='{.status.ancestors[0].conditions[0].reason}'; echo
sleep 5
for i in $(seq 1 20); do curl -s -o /dev/null -w "%{http_code}\n" todo.localhost:8080/flaky; done | sort | uniq -c
kubectl -n todo logs $BAD -c app --since=15s | grep -c 503
```

**이렇게 나오면 성공**: 손님 쪽 20번 **모두 200**. 그런데 고장 난 파드의 로그에는 503이 여전히 여러 줄 — 재시도가 실패를 손님에게서 **숨겼을 뿐**, 고장 난 파드는 계속 요청을 받습니다

```
backendtrafficpolicy.gateway.envoyproxy.io/flaky created
Accepted
     20 200
9
```

<details><summary><b>이렇게 나오면?</b> — 자주 나는 오류와 해결 (눌러서 펼치기)</summary>

| 화면 | 원인 | 해결 |
|---|---|---|
| `echo $BAD`가 빈 줄 | flaky 파드가 없음 | 1단계 |
| `touch: /tmp/broken: Read-only file system` | (이 파일대로면 안 남) `securityContext`를 더함 | 위 파일 그대로 |
| 재시도 뒤에도 503이 섞임 | apply 직후 | 5초 뒤 다시 |
| reason이 빈 줄 | `targetRefs`의 이름 오타 | `name: flaky` |
| `grep -c` 결과가 `0` | 새 터미널이라 `$BAD`가 빔 | 가의 첫 줄 `BAD=…`부터 다시 |

</details>

## 4단계. 고장 난 파드 빼기

`flaky-policy.yaml` 맨 아래(`retry:` 덩어리 다음, `retry:`와 같은 칸)에 이어 붙입니다.

```bash
nano flaky-policy.yaml
```

```yaml
  healthCheck:
    passive:
      consecutive5XxErrors: 3
      interval: 5s
      baseEjectionTime: 30s
      maxEjectionPercent: 50
```

| 줄 | 뜻 |
|---|---|
| `healthCheck: passive:` | 따로 검사 요청을 보내지 않고, 오가는 요청의 결과만 보고 판단 |
| `consecutive5XxErrors: 3` | 같은 파드에서 5xx가 **3번 연달아** 나면 |
| `baseEjectionTime: 30s` | 그 파드를 **30초** 뺌. 다시 넣었는데 또 실패하면 더 길게 |
| `maxEjectionPercent: 50` | 파드의 절반까지만 뺌(다 빼면 갈 곳이 없음) |
| `interval: 5s` | 빼 둔 파드를 다시 넣을지 따져 보는 간격 |

```bash
kubectl apply -f flaky-policy.yaml
sleep 20
for i in $(seq 1 20); do curl -s -o /dev/null -w "%{http_code}\n" todo.localhost:8080/flaky; done | sort | uniq -c
kubectl -n todo logs $BAD -c app --since=5s | grep -c 503
```

**이렇게 나오면 성공**: 20번 모두 200, 그리고 고장 난 파드가 최근 5초에 받은 요청이 **0** — 명단에서 빠졌습니다

```
backendtrafficpolicy.gateway.envoyproxy.io/flaky configured
     20 200
0
```

- 처음 몇 번은 고장 난 파드로 갔다가(연달아 3번 실패해야 빠짐) 빠집니다. 30초 뒤 다시 들어가 시험받고, 또 실패하면 이번엔 더 오래 빠집니다
- `0`이 아니라 `3` 안팎이면 마침 다시 들어간 때입니다. 10초 뒤 마지막 두 줄을 다시

<details><summary><b>이렇게 나오면?</b> — 자주 나는 오류와 해결 (눌러서 펼치기)</summary>

| 화면 | 원인 | 해결 |
|---|---|---|
| 로그 수가 계속 10쯤 | `healthCheck`가 `spec` 밖(칸) — 또는 적용 직후 | `cat flaky-policy.yaml`에서 `retry:`와 `healthCheck:`가 같은 칸인지, 20초 뒤 다시 |
| `unknown field "consecutive5xxErrors"` | 대소문자 — `5Xx` | `consecutive5XxErrors` |
| 200이 아닌 줄이 섞임 | 3단계의 `retry:`를 지움 | 3단계 내용 + 이 단계 내용 둘 다 |

</details>

## 5단계. 동시 요청 한도 — 넘치면 바로 거절

먼저 고장을 고칩니다. 그다음 0.5초 걸리는 요청 10개를 **동시에** 보냅니다.

```bash
kubectl -n todo exec $BAD -c app -- rm /tmp/broken
seq 1 10 | xargs -P 10 -I{} curl -s -o /dev/null -w "%{http_code} %{time_total}\n" "todo.localhost:8080/flaky?delay=500" | sort
```

**이렇게 나오면 성공**: 10개 모두 `200`, 모두 0.5초쯤 — 몰려도 다 받아 줌

```
200 0.503861
...(10줄 모두 200 0.50…)
```

이제 `flaky-policy.yaml` 맨 아래(`healthCheck:`와 같은 칸)에 이어 붙입니다.

```yaml
  circuitBreaker:
    maxConnections: 2
    maxPendingRequests: 1
    maxParallelRequests: 2
```

| 줄 | 뜻 |
|---|---|
| `maxConnections: 2` | flaky로 동시에 여는 연결은 2개까지 |
| `maxPendingRequests: 1` | 연결을 기다리는 줄에는 1개까지 |
| `maxParallelRequests: 2` | 동시에 처리 중인 요청은 2개까지 |
| (넘치면) | 기다리지 않고 **바로 503** |

```bash
nano flaky-policy.yaml
kubectl apply -f flaky-policy.yaml
sleep 15
seq 1 10 | xargs -P 10 -I{} curl -s -o /dev/null -w "%{http_code} %{time_total}\n" "todo.localhost:8080/flaky?delay=500" | sort
curl -s "todo.localhost:8080/flaky?delay=500" & curl -s "todo.localhost:8080/flaky?delay=500" & curl -s "todo.localhost:8080/flaky?delay=500" & curl -s "todo.localhost:8080/flaky?delay=500"; sleep 1; echo
```

**이 명령은**: 한도를 넣고, 같은 10개를 동시에 보냄. 마지막 줄 = 4개를 동시에 보내 넘친 쪽의 본문을 봄.

**이렇게 나오면 성공**: 200은 **셋쯤**(둘은 0.5초, 하나는 줄에서 기다려 1초쯤 — 도착 순서에 따라 둘일 때도 있음), 나머지는 **바로**(0.00…초) `503`. 넘친 쪽 본문은 `reset reason: overflow`

```
backendtrafficpolicy.gateway.envoyproxy.io/flaky configured
200 0.502958
200 0.503902
200 1.005872
503 0.000661
503 0.000899
503 0.001011
503 0.001020
503 0.001124
503 0.001854
503 0.003136
upstream connect error or disconnect/reset before headers. reset reason: overflow{"pod":"flaky-789cb8fddf-dvhjz","code":200}
...
```

| | 한도 없음 | 연결 2 + 줄 1 |
|---|---|---|
| 동시 10개(각 0.5초) | 10개 모두 0.5초에 `200` | `200` 셋쯤, 나머지 `503` |
| 넘친 손님 | — | 기다리지 않고 1~5밀리초 만에 "지금은 안 됨" |
| 앱이 받는 양 | 몰리는 만큼 다 | 한도만큼만 |

| 증상 | 이 실습에서 | 어디에 적나 | 서비스 메시(Istio)에서 |
|---|---|---|---|
| 느리다 | 2단계 타임아웃 | HTTPRoute `timeouts` | VirtualService `timeout` (메시 실습 5) |
| 가끔 실패 | 3단계 재시도 | BackendTrafficPolicy `retry` | VirtualService `retries` (메시 실습 5) |
| 한 파드가 계속 실패 | 4단계 고장 난 파드 빼기 | BackendTrafficPolicy `healthCheck.passive` | DestinationRule `outlierDetection` |
| 한꺼번에 몰림 | 5단계 동시 요청 한도 | BackendTrafficPolicy `circuitBreaker` | DestinationRule `connectionPool` |
| 누가 지키나 | 입구(바깥 손님 → 앱) | | 부르는 서비스 옆 사이드카(서비스 → 서비스) |

<details><summary><b>이렇게 나오면?</b> — 자주 나는 오류와 해결 (눌러서 펼치기)</summary>

| 화면 | 원인 | 해결 |
|---|---|---|
| 한도를 넣었는데 10개 모두 200 | apply 직후, 또는 `circuitBreaker`가 `spec` 밖 | 15초 뒤 다시, `cat flaky-policy.yaml` |
| 첫 명령(한도 없이)에서 503이 섞임 | `rm /tmp/broken`을 안 함 | 첫 줄 |
| `xargs: curl: …` 오류 | 줄을 나눠 붙여 넣음 | 한 줄 그대로 |
| 504가 섞임 | `delay`를 2초 넘게 줌(2단계 한도) | `delay=500` |

## 끝났는지 확인
- ☐ 1단계 5초짜리 `200 5.0…`, 20초짜리 `504 15.0…`
- ☐ 2단계 5초짜리 `504 2.0…`, flaky 로그에 `delay=5000 200`
- ☐ 3단계 고장 뒤 503이 섞임 → 재시도 뒤 20번 모두 `200`, 고장 파드 로그는 여러 줄
- ☐ 4단계 20번 모두 `200`, 고장 파드 로그 `0`
- ☐ 5단계 동시 10개 → `200` 셋쯤 + 나머지 `503`(바로)

## 정리
- `/tmp/broken`은 5단계 첫 줄에서 지웠습니다. flaky와 정책은 둡니다(실습 8에서 HTTPS로 옮길 때 같이 옮김)
- 미션 도전 B가 2단계의 `timeouts`를 쇼핑몰에 씁니다
