# 실습 5. 속도 제한과 게이트웨이 지표

**무엇을 하나요**: 실습 3의 API 키 정책이 붙여 주는 `x-client-id`마다 **1분에 5번**까지만 받게 합니다. 6번째부터 429가 나오고, 다른 손님은 따로 세는 것을 봅니다. 먼저 제한 없이 한 손님이 몇 번이든 부를 수 있는 것을 봅니다. 마지막에 Envoy의 숫자판을 모니터링 과목의 **Prometheus**가 가져가게 해서, 입구에서 막힌 401·429가 몇 개인지 보고 **앱의 숫자판에는 그 요청이 없다**는 것을 대조합니다. (교안 05장)

**필요한 것**: 실습 3의 키 정책, 모니터링 과목의 Prometheus(`prometheus.localhost`).

## 1단계. 제한 없이 7번

```bash
cd ~/apigw
for i in $(seq 1 7); do curl -s -o /dev/null -w "%{http_code} " -H "x-api-key: key-aaa" todo.localhost:8080/api/todos; done; echo
```

**이 명령은**: team-a의 키로 7번 연달아 부르고 상태 코드만 한 줄로 찍음(3단계에서 다시 씀).

**이렇게 나오면 성공**

```
200 200 200 200 200 200 200
```

- 7번이든 7만 번이든 다 받습니다. 한 손님이 몰아치면 같은 앱을 쓰는 다른 손님까지 영향을 받을 수 있습니다
- 앱마다 "누가 몇 번 불렀나"를 세는 코드를 넣는 대신 입구에서 셉니다

## 2단계. 속도 제한 정책 쓰기

```bash
nano ratelimit.yaml
```

```yaml
apiVersion: gateway.envoyproxy.io/v1alpha1
kind: BackendTrafficPolicy
metadata:
  name: ratelimit
  namespace: todo
spec:
  targetRefs:
  - group: gateway.networking.k8s.io
    kind: HTTPRoute
    name: todo-api
  rateLimit:
    type: Local
    local:
      rules:
      - clientSelectors:
        - headers:
          - name: x-client-id
            type: Distinct     # 값(team-a, team-b)마다 따로 센다
        limit:
          requests: 5
          unit: Minute
```

| 부분 | 뜻 |
|---|---|
| `kind: BackendTrafficPolicy` | 앱으로 가는 요청의 흐름을 다루는 정책(횟수 제한, 부록의 재시도·타임아웃 등) |
| `targetRefs` → `todo-api` | 실습 3과 같은 HTTPRoute(`/api`)에 하나 더 붙임 |
| `type: Local` | Envoy 파드 안에서 셈 |
| `clientSelectors` → `x-client-id`, `type: Distinct` | 키 정책이 붙여 준 이름**마다** 따로 셈 |
| `limit: requests: 5, unit: Minute` | 1분에 5번 |

```bash
kubectl apply -f ratelimit.yaml
kubectl -n todo get backendtrafficpolicy ratelimit -o jsonpath='{.status.ancestors[0].conditions[0].reason}'; echo
```

**이렇게 나오면 성공**

```
backendtrafficpolicy.gateway.envoyproxy.io/ratelimit created
Accepted
```

## 3단계. team-a로 7번, 그때 team-b는

```bash
for i in $(seq 1 7); do curl -s -o /dev/null -w "%{http_code} " -H "x-api-key: key-aaa" todo.localhost:8080/api/todos; done; echo
curl -s -o /dev/null -w "%{http_code}\n" -H "x-api-key: key-bbb" todo.localhost:8080/api/todos
```

**이렇게 나오면 성공**

```
200 200 200 200 200 429 429
200
```

- 429 = Too Many Requests. team-b는 따로 세므로 200입니다
- 1분 안에 다시 해 보면 처음부터 429일 수 있습니다. 조금 기다리면 다시 200

<details><summary><b>이렇게 나오면?</b> — 자주 나는 오류와 해결 (눌러서 펼치기)</summary>

| 화면 | 원인 | 해결 |
|---|---|---|
| 처음부터 `429` | 바로 전에 시험한 요청이 남아 있음 | 4단계의 `x-ratelimit-reset`초만큼 기다렸다 다시 |
| 7번 모두 `200` | 정책 적용 전, 또는 `targetRefs` 이름 오타 | 10초 뒤 다시, 2단계 reason이 `Accepted`인지 |
| 7번 모두 `401` | 키 오타, 또는 실습 3 정책이 없음 | `kubectl -n todo get securitypolicy apikey` |
| team-b도 `429` | `type: Distinct`가 빠짐 | 줄 추가 후 apply, 1분 뒤 다시 |

</details>

## 4단계. 429 응답 들여다보기

```bash
curl -s -D - -H "x-api-key: key-aaa" todo.localhost:8080/api/todos; echo
```

**이 명령은**: 한도를 넘긴 team-a로 한 번 더 부르고 응답 헤더까지 봄.

**이렇게 나오면 성공**

```
HTTP/1.1 429 Too Many Requests
content-length: 18
content-type: text/plain
x-ratelimit-limit: 5
x-ratelimit-remaining: 0
x-ratelimit-reset: 12
date: Sat, 17 Oct 2026 14:55:38 GMT

local_rate_limited
```

| 헤더 | 뜻 |
|---|---|
| `x-ratelimit-limit: 5` | 한도(1분에 5번) |
| `x-ratelimit-remaining: 0` | 남은 횟수 |
| `x-ratelimit-reset: 12` | 몇 초 뒤 다시 채워지나 — 손님 프로그램은 이만큼 기다렸다 다시 부르면 됨 |

- 3단계에서 1분 넘게 지났으면 `200`이 나옵니다. 그때는 3단계 첫 줄을 한 번 더 친 뒤 바로 이 명령을 칩니다

## 5단계. Envoy 지표를 Prometheus로

Envoy는 처음부터 요청 수를 세고 있습니다(파드의 `19001`번, `/stats/prometheus`). 모니터링 과목의 Prometheus가 그 숫자를 가져가게 PodMonitor를 만듭니다(모니터링 실습 3과 같은 방식).

```bash
nano envoy-podmonitor.yaml
```

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PodMonitor
metadata:
  name: envoy-proxy
  namespace: envoy-gateway-system
spec:
  selector:
    matchLabels:
      app.kubernetes.io/component: proxy
      app.kubernetes.io/managed-by: envoy-gateway
  podMetricsEndpoints:
  - port: metrics
    path: /stats/prometheus
```

| 줄 | 뜻 |
|---|---|
| `namespace: envoy-gateway-system` | Envoy 파드가 있는 곳 |
| `matchLabels` 두 줄 | Envoy Gateway가 띄운 Envoy 파드의 이름표 |
| `port: metrics` · `path: /stats/prometheus` | 파드의 `metrics`(19001) 포트, 숫자판 주소 |

```bash
kubectl apply -f envoy-podmonitor.yaml
```

**이렇게 나오면 성공**: `podmonitor.monitoring.coreos.com/envoy-proxy created`. 1분쯤 뒤 Prometheus(`http://prometheus.localhost:<80을 전달한 포트>`) **Status → Target health**에 `podMonitor/envoy-gateway-system/envoy-proxy/0` `UP`(주소 `http://<Envoy 파드 IP>:19001/stats/prometheus`).

<details><summary><b>이렇게 나오면?</b> — 자주 나는 오류와 해결 (눌러서 펼치기)</summary>

| 화면 | 원인 | 해결 |
|---|---|---|
| 2분이 지나도 대상이 없음 | 라벨 오타 | `kubectl -n envoy-gateway-system get pods --show-labels \| grep proxy`와 비교 |
| `DOWN` | `port` 이름 오타 | `metrics` 그대로 |
| Prometheus 화면이 안 열림 | 80을 전달하지 않음(8080 아님) | PORTS 탭에서 80 |

</details>

## 6단계. 막힌 401·429는 몇 개 — 게이트웨이 대 앱

Prometheus **Query**에 하나씩 넣고 **Execute**를 누릅니다(30초쯤 뒤).

```promql
sum by (envoy_response_code_class) (envoy_http_downstream_rq_xx)
envoy_http_api_key_auth_unauthorized
envoy_http_jwt_authn_denied
envoy_http_local_rate_limit_rate_limited
sum by (envoy_response_code_class) (envoy_cluster_upstream_rq_xx{envoy_cluster_name=~"httproute/todo/todo-api.*"})
```

**이렇게 나오면 성공** — 숫자는 지금까지 부른 횟수라 사람마다 다릅니다

| 쿼리 | 뜻 | 결과 (강사 VM) |
|---|---|---|
| 첫째 | 입구가 **손님에게 돌려준** 응답, 앞자리별 | `2` 377 · `4` 29 |
| 둘째 | API 키로 막은 수(401) | 14 |
| 셋째 | JWT로 막은 수(401) | 7 |
| 넷째 | 속도 제한으로 막은 수(429) | 5 |
| 다섯째 | `/api`에서 **앱까지 간** 요청의 응답, 앞자리별 | `2` 158 · `4` 1 |

이번에는 **앱의 숫자판**을 직접 봅니다(모니터링 실습 4에서 단 지표 — v2도 같은 소스).

```bash
kubectl -n todo exec deploy/load -c curl -- curl -s http://api-v2:3000/metrics | grep "^todo_http_requests_total"
```

**이렇게 나오면 성공**: 200만 있고 401·429 줄은 없음

```
todo_http_requests_total{method="GET",route="/api/health",code="200"} 66
todo_http_requests_total{method="GET",route="/api/me",code="200"} 17
todo_http_requests_total{method="GET",route="/api/todos",code="200"} 21
```

| | 게이트웨이 지표 (Envoy) | 앱 지표 (todo-api `/metrics`) |
|---|---|---|
| 막힌 401 (키·토큰) | 있음 — 둘째·셋째 쿼리 | 없음 |
| 막힌 429 (횟수) | 있음 — 넷째 쿼리 | 없음 |
| 통과한 요청 | 있음 — 다섯째 쿼리 | 있음 — 경로별 |
| 이것만 보면 | 앱 안의 경로·업무 숫자를 모름 | **막힌 손님이 있었는지 모름** |

<details><summary><b>이렇게 나오면?</b> — 자주 나는 오류와 해결 (눌러서 펼치기)</summary>

| 화면 | 원인 | 해결 |
|---|---|---|
| 모두 `Empty query result` | 5단계 대상이 아직 UP 전 | Target health 확인 후 1분 뒤 |
| 넷째가 빈 결과 | 3단계에서 429를 한 번도 못 봄 | 3단계 첫 줄을 다시 친 뒤 30초 뒤 |
| 마지막 명령이 빈 결과 | v2를 `lab/docker/todo/api`로 만듦(지표 없음) | 실습 2의 3단계 오류 표 — 이 명령만 건너뜀 |

</details>

## 끝났는지 확인
- ☐ 정책 전 team-a 7번 모두 `200`
- ☐ 정책 후 `200 200 200 200 200 429 429`, 그 직후 team-b `200`
- ☐ 429 응답에 `x-ratelimit-limit: 5`
- ☐ Target health에 `podMonitor/envoy-gateway-system/envoy-proxy/0` `UP`
- ☐ 넷째 쿼리(429 수)가 1 이상, 앱 숫자판에는 200만
