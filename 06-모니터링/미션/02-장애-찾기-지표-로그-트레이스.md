# 미션 2. 장애 찾기 — 지표 · 로그 · 트레이스

**상황**: 손님들이 "쇼핑몰이 이상하다"고 합니다. 아래 [준비](#준비--장애-넣기)에서 여러분이 직접 스크립트를 실행해 쇼핑몰(`shop`)에 **장애를 하나** 넣습니다. 무엇이 고장 나는지는 알려 주지 않습니다. 지금까지 만든 도구로 찾습니다.

- **지표**로 무엇이 나빠졌는지(얼마나, 어느 서비스) → **로그**로 언제부터, 어떤 요청이 → **트레이스**로 요청 하나의 어디에서 → 마지막에 원인을 확인하고 되돌린 뒤, 짧은 **장애 보고**를 씁니다
- 장애를 찾기 전에는 `kubectl describe`·`kubectl get … -o yaml`로 설정을 뒤지지 않습니다. 회사에서는 무엇을 볼지부터 모르는 경우가 많고, 이 미션은 관측 도구로 범위를 좁히는 연습입니다

언제: 실습 8(08장) 뒤. 필요한 것: 미션 1(shop 사이드카 지표·대시보드), 실습 6(Loki), 실습 7(Tempo·Telemetry), 실습 8(경보).

## 준비 — 장애 넣기

```bash
cd ~/ktcloud-cloud-native-lab && git pull && cd lab
bash monitoring/break-shop.sh
```

**이 명령은**: 내 쇼핑몰에 장애를 하나 넣습니다. 무엇을 넣었는지는 출력하지 않습니다. 답이 보이므로 **스크립트 파일은 열어 보지 않습니다.**

**이렇게 나오면 성공** (시각은 사람마다 다름 — 결과 정리 표에 적어 둡니다)

```
장애를 하나 넣었습니다 — 14:05:31
```

## 과제 1. 지표 — 무엇이 나빠졌나

미션 1의 대시보드 `shop 골든 시그널`(또는 Prometheus Query)에서 세 가지 골든 시그널을 봅니다. 결과 정리 표에 적습니다.

- 요청 수는 어떻게 바뀌었나요?
- 오류(5xx 비율)는?
- 지연(p95)은 — **어느 서비스들**이, 얼마나?

<details><summary>힌트 1 — 어디부터</summary>

대시보드 오른쪽 위 시간 범위를 **Last 30 minutes**로 두고 세 패널이 꺾인 곳을 찾습니다. Prometheus라면 미션 1 과제 2의 세 쿼리를 `$workload` 대신 `.*`로 바꿔 넣습니다.
</details>
<details><summary>힌트 2 — 지연이 큰 서비스가 여럿일 때</summary>

여러 서비스가 함께 느려졌다면, 그 서비스들이 **공통으로 부르는** 서비스를 의심합니다. 실습 7의 주문 트레이스(6단계)에서 누가 누구를 불렀는지 떠올려 봅니다.
</details>

## 과제 2. 로그 — 언제부터, 어떤 요청이

Grafana Explore(Loki)에서 frontend 로그로 **느린 요청**만 고르고, 처음 나타난 시각과 어떤 주소(경로)들인지 찾습니다.

<details><summary>힌트 1 — 어떤 필드</summary>

frontend 로그는 JSON이고 걸린 시간이 `http.resp.took_ms`에 있습니다. 실습 6의 5단계.
</details>
<details><summary>힌트 2 — 경로별로 세기</summary>

`sum by (http_req_path) (count_over_time({…} | json | … [5m]))` — 실습 6의 6단계 모양에 `| json`과 조건을 더합니다.
</details>

## 과제 3. 트레이스 — 어디서

Grafana Explore(Tempo)에서 1초 넘게 걸린 트레이스를 찾아 하나를 열고, **어느 스팬이 시간을 거의 다** 썼는지 찾습니다.

<details><summary>힌트 1 — TraceQL</summary>

실습 7 확인 문제 2에서 쓴 `{duration > …}`.
</details>
<details><summary>힌트 2 — 계단 읽기</summary>

막대가 가장 긴 **맨 아래** 스팬을 찾습니다. 위 스팬들은 아래 스팬을 기다린 시간까지 포함합니다(실습 7의 5단계).
</details>

## 과제 4. 원인 확인, 되돌리기, 장애 보고

과제 1~3으로 범위를 좁혔으면 이제 그 서비스의 **최근 변경**을 확인합니다. 원인을 찾으면 되돌리고, 지표가 정상으로 돌아오는 것까지 확인한 뒤 아래 양식으로 장애 보고를 씁니다.

```
[장애 보고]
무엇이   : (손님이 겪은 일 한 줄 — 예: 쇼핑몰 화면이 느림)
언제부터 : (시각 — 로그·그래프에서)
영향     : (숫자로 — p95가 얼마에서 얼마로, 오류율, 요청 수)
원인     : (어느 서비스의 무엇 — 근거가 된 지표·로그·트레이스)
조치     : (한 명령과 그 뒤 확인한 숫자)
```

<details><summary>힌트 1 — 최근 변경</summary>

`kubectl -n shop get pods` — 다른 파드보다 **AGE가 짧은** 파드가 있나요? 그 Deployment를 `kubectl -n shop describe deploy <이름>`으로 보고 환경변수(Environment)를 읽습니다.
</details>
<details><summary>힌트 2 — 되돌리기</summary>

환경변수 하나를 지우는 명령은 `kubectl -n shop set env deploy/<이름> <변수 이름>-`(끝의 `-`가 지우기).
</details>
