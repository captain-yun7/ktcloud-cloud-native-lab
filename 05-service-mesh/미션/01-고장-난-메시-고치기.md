# 미션. 고장 난 메시 고치기

**무엇을 하나요**: 실습 6의 쇼핑몰(`shop`)에 **고장 4개**가 숨은 메시 설정을 적용합니다. 쇼핑몰 화면이 깨집니다. 교안 06장의 순서(응답 코드 → 오류 문구 → Kiali → `istioctl analyze` → 규칙 목록)로 고장을 하나씩 찾아 고칩니다. 앱은 하나도 고장 나지 않았습니다. 고장은 모두 **메시 설정**에 있습니다.

> **바로 가기** · [준비](#준비) · [목표](#목표) · [지킬 것](#지킬-것) · [찾는 순서](#찾는-순서) · [힌트](#힌트) · [결과 정리 표](#결과-정리-표) · [도전 (선택)](#도전-선택) · [정리](#정리)

## 준비

```bash
cd ~/ktcloud-cloud-native-lab && git pull
kubectl apply -f 05-service-mesh/mesh-broken.yaml
for p in / /product/OLJCESPC7Z /cart; do echo "$p $(curl -s -m 10 -o /dev/null -w '%{http_code}' shop.localhost$p)"; done
```

**이렇게 나오면 고장 난 것**: 세 페이지 모두 200이 아닙니다.

## 목표
- `shop.localhost`의 **홈(`/`) · 상품(`/product/OLJCESPC7Z`) · 장바구니(`/cart`)** 를 20번씩 불러 **모두 200**
- `istioctl analyze -n shop` → `No validation issues found`

```bash
for p in / /product/OLJCESPC7Z /cart; do printf "%s " $p; for i in $(seq 1 20); do curl -s -m 10 -o /dev/null -w "%{http_code}\n" shop.localhost$p; done | sort | uniq -c | tr -s " " | tr "\n" ","; echo; done
```

## 지킬 것
- 메시 안 서비스끼리는 mTLS만 받기(PeerAuthentication `default`의 `STRICT`)는 **그대로 둡니다**
- cartservice를 부를 수 있는 것은 **frontend와 checkoutservice뿐**입니다
- 앱(Deployment)은 고치지 않습니다. 고칠 곳은 모두 메시 설정입니다
- 고장마다 **증상 → 찾은 방법 → 원인 → 고친 내용**을 결과 정리 표에 적습니다

## 찾는 순서

| 순서 | 보는 것 | 명령 · 화면 |
|---|---|---|
| 1 | 파드가 다 떠 있나 | `kubectl -n shop get pods` — 모두 `2/2`? |
| 2 | 응답 코드 | 위 목표의 반복문 — 502? 500? |
| 3 | 오류 문구 | `curl -s shop.localhost/cart \| grep -o "rpc error[^<]*" \| head -3` |
| 4 | 어느 화살표가 빨간가 | Kiali Traffic Graph (shop) |
| 5 | 설정 점검 | `istioctl analyze -n shop` |
| 6 | 걸린 규칙 | `kubectl -n shop get peerauthentication,authorizationpolicy,destinationrule,virtualservice` |

- `istioctl analyze`가 하나만 알려 줘도 고장이 하나라는 뜻은 아닙니다
- 하나를 고쳐도 화면이 그대로일 수 있습니다. 그때는 **오류 문구가 바뀌었는지** 보세요

## 힌트

<details><summary>힌트 1 — 502 Bad Gateway</summary>

`shop.localhost`의 입구 Traefik은 **메시 밖**에 있어 평문으로 frontend를 부릅니다. 네임스페이스 전체에 걸린 PeerAuthentication을 보세요. STRICT는 그대로 두고, **frontend만** 평문도 받게 하는 PeerAuthentication을 하나 더 만들 수 있습니다(`selector`로 frontend를 고름).
</details>
<details><summary>힌트 2 — no healthy upstream</summary>

`istioctl analyze -n shop`이 알려 주는 DestinationRule의 subset 라벨과 실제 파드 라벨(`kubectl -n shop get pods --show-labels | grep productcatalog`)을 비교하세요.
</details>
<details><summary>힌트 3 — fault filter abort</summary>

이 문구는 앱이 아니라 프록시가 만든 응답입니다(실습 5). `kubectl -n shop get virtualservice`에서 `fault`가 든 규칙을 찾으세요.
</details>
<details><summary>힌트 4 — RBAC: access denied</summary>

cartservice에 걸린 AuthorizationPolicy의 `principals`(허용할 신분 목록)를 보세요. 신분 이름은 `cluster.local/ns/<네임스페이스>/sa/<서비스 계정>` 모양이고, Online Boutique는 서비스마다 같은 이름의 서비스 계정을 씁니다(`kubectl -n shop get sa`).
</details>

## 도전 (선택)

**frontend 카나리** — 쇼핑몰 새 디자인(Cymbal 브랜딩)을 메시 안 손님 10%에게만, 헤더 `x-canary: true`는 항상 새 디자인. 실습 4의 `canary.yaml`에서 서비스만 바꾸면 됩니다.

```bash
kubectl -n shop patch deploy frontend -p '{"spec":{"template":{"metadata":{"labels":{"version":"v1"}}}}}'
kubectl apply -f ~/ktcloud-cloud-native-lab/05-service-mesh/frontend-v2.yaml
kubectl -n shop run curl --image=curlimages/curl:8.16.0 -- sleep infinity
kubectl -n shop exec curl -c curl -- sh -c 'for i in $(seq 1 100); do curl -s http://frontend/ | grep -c "Cymbal Shops"; done' | sort | uniq -c
#   0 = 지금 디자인, 1 = 새 디자인
```

- 확인: 메시 안(`curl` 파드) 100번 중 `1`이 10번 안팎, 헤더 5번 모두 `1`
- 그다음 VM에서 `curl -s shop.localhost`로 100번 세어 보세요. 왜 다르게 나올까요?

## 정리

미션에서 넣은 메시 설정을 모두 지웁니다(모니터링 과목은 고장 없는 shop에서 시작).

```bash
kubectl -n shop delete peerauthentication,authorizationpolicy,destinationrule,virtualservice --all
kubectl -n shop delete deploy frontend-v2 --ignore-not-found
kubectl -n shop delete pod curl --ignore-not-found
for p in / /product/OLJCESPC7Z /cart; do echo "$p $(curl -s -m 10 -o /dev/null -w '%{http_code}' shop.localhost$p)"; done
```

- 세 줄 모두 `200`이면 끝. shop·Prometheus·Kiali는 그대로 둡니다
