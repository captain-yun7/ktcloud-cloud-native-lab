# 실습 5. 타임아웃 · 재시도 · 장애 주입

**무엇을 하나요**: api가 **느려지거나 일부 실패하는 상황**을 메시로 일부러 만들고(장애 주입), 규칙이 **없을 때** 손님이 어떻게 되는지 먼저 봅니다. 그다음 코드를 고치지 않고 VirtualService 한 장씩으로 **느린 응답 끊기(타임아웃)** 와 **실패한 요청 다시 보내기(재시도)** 를 겁니다. (교안 05장)

**필요한 것**: 실습 4의 todo(Istio 주입, `load`, `L` 변수).

규칙을 파일 네 개로 만들어 차례로 적용합니다. `api-…` 두 파일은 이름이 `api`인 VirtualService라 적용하면 실습 4의 `canary.yaml` 규칙을 덮어씁니다. `web-…` 두 파일은 이름이 `web`입니다.

| 파일 | 어디에 거나 | 무엇을 |
|---|---|---|
| `api-delay.yaml` | web → api | api로 가는 요청을 모두 2초 늦춤 (장애 주입 — 지연) |
| `web-timeout.yaml` | load → web | web이 1초 안에 답이 없으면 끊음 (타임아웃) |
| `api-abort.yaml` | web → api | api로 가는 요청의 50%를 503으로 (장애 주입 — 실패) |
| `web-retry.yaml` | load → web | web이 5xx로 답하면 3번까지 다시 보냄 (재시도) |

## 1단계. api에 2초 지연 주입 — 규칙 없으면 기다림

**가. 지금** — 할 일 목록 한 번에 걸리는 시간.

```bash
cd ~/mesh
L="kubectl -n todo exec deploy/load -c curl --"      # 새 터미널이면
$L curl -s -o /dev/null -w "%{http_code} %{time_total}s\n" http://web/api/todos
```

```
200 0.005114s
```

**나. api를 2초 늦추기**

```bash
nano api-delay.yaml
```

```yaml
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata: {name: api, namespace: todo}
spec:
  hosts: [api]
  http:
  - fault:
      delay: {percentage: {value: 100}, fixedDelay: 2s}
    route:
    - destination: {host: api}
```

```bash
kubectl apply -f api-delay.yaml
for i in 1 2 3; do $L curl -s -o /dev/null -w "%{http_code} %{time_total}s\n" http://web/api/todos; done
```

**이 명령은**: web → api 요청을 web 옆 프록시가 모두(`value: 100`) 2초 붙잡았다 보냄. api 코드는 그대로입니다. `-w "%{http_code} %{time_total}s"` = 응답 코드와 걸린 시간만 찍음.

**이렇게 나오면 성공**: 세 번 모두 **200, 2초**. 규칙이 없으니 손님(`load`)도 2초를 그대로 기다립니다. 10초 걸리면 10초를 기다립니다.

```
200 2.006202s
200 2.006459s
200 2.006935s
```

## 2단계. 타임아웃 1초

```bash
nano web-timeout.yaml
```

```yaml
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata: {name: web, namespace: todo}
spec:
  hosts: [web]
  http:
  - timeout: 1s
    route:
    - destination: {host: web}
```

```bash
kubectl apply -f web-timeout.yaml
for i in 1 2 3; do $L curl -s -w " %{http_code} %{time_total}s\n" http://web/api/todos; done
$L curl -s -o /dev/null -w "%{http_code} %{time_total}s\n" http://web/
```

**이 명령은**: web을 부른 요청이 1초 안에 답이 없으면 **부르는 쪽(load 옆) 프록시가 끊고** 504를 돌려줌. 마지막 줄 = api를 부르지 않는 홈 화면(`/`).

**이렇게 나오면 성공**: 할 일 목록은 1초에 504로 끊기고(1단계의 2초와 비교), 홈은 그대로 빠름.

```
upstream request timeout 504 1.001955s
upstream request timeout 504 1.001164s
upstream request timeout 504 1.000761s
200 0.004830s
```

| | 규칙 없음 (1단계) | 타임아웃 1초 (지금) |
|---|---|---|
| 할 일 목록 (`/api/todos`, api가 2초) | `200`, 2초 기다림 | `504`, 1초에 끊김 |
| 홈 (`/`, api 안 부름) | `200`, 0.005초 | `200`, 0.005초 |

<details><summary><b>이렇게 나오면?</b> — 자주 나는 오류와 해결 (눌러서 펼치기)</summary>

| 화면 | 원인 | 해결 |
|---|---|---|
| 여전히 `200 2.0…s` | 적용 직후, 또는 `apply`를 안 함 | 5초 뒤 다시. `kubectl -n todo get vs` 에 `web`이 있는지 |
| `0.00…s`로 바로 `200` | 1단계 지연 규칙이 없음(카나리 규칙 그대로) | `kubectl apply -f api-delay.yaml` |

</details>

## 3단계. api에 50% 실패 주입 — 재시도 없이

```bash
nano api-abort.yaml
```

```yaml
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata: {name: api, namespace: todo}
spec:
  hosts: [api]
  http:
  - fault:
      abort: {percentage: {value: 50}, httpStatus: 503}
    route:
    - destination: {host: api}
```

```bash
kubectl -n todo delete vs web
kubectl apply -f api-abort.yaml
$L sh -c 'for i in $(seq 1 100); do curl -s -o /dev/null -w "%{http_code}\n" http://web/api/todos; done' | sort | uniq -c
$L curl -s -w " %{http_code}\n" http://web/api/todos
```

**이 명령은**: 2단계의 타임아웃 규칙(`web`)을 지우고, web → api 요청의 50%를 web 옆 프록시가 503으로 바로 돌려주게 함. 100번 보내 응답 코드별로 셈. 마지막 줄 = 응답 본문 한 번 보기.

**이렇게 나오면 성공**: 절반쯤 503. 실패한 응답의 본문은 `fault filter abort`(프록시가 만든 응답, 여러 번 치면 할 일 목록과 번갈아 나옴).

```
     42 200
     58 503
```
```
fault filter abort 503
```

- api는 멀쩡합니다. **프록시가** 일부러 503을 돌려준 것입니다. "api가 절반 실패하면 손님은?"을 코드 수정 없이 시험했고, 답은 "손님도 절반 실패"입니다

## 4단계. 재시도 3회

```bash
nano web-retry.yaml
```

```yaml
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata: {name: web, namespace: todo}
spec:
  hosts: [web]
  http:
  - retries: {attempts: 3, retryOn: 5xx}
    route:
    - destination: {host: web}
```

```bash
kubectl apply -f web-retry.yaml
$L sh -c 'for i in $(seq 1 100); do curl -s -o /dev/null -w "%{http_code}\n" http://web/api/todos; done' | sort | uniq -c
```

**이 명령은**: web이 5xx로 답하면 부르는 쪽(load 옆) 프록시가 **3번까지 다시** 보냄. 다시 보낸 요청도 web → api에서 주사위를 다시 굴립니다.

**이렇게 나오면 성공**: 503이 몇 개만 남음(0.5 × 0.5 × 0.5 × 0.5 ≈ 6%).

```
     93 200
      7 503
```

| | 재시도 없음 (3단계) | 재시도 3회 (지금) |
|---|---|---|
| 100번 중 503 (강사 VM) | 58, 60 | 7, 4 |
| api에 간 요청 수 | 100 | 더 많음 — 실패할 때마다 최대 3번 더 |

- 재시도는 **잠깐 실패하는** 고장에 효과가 있습니다. api가 완전히 멈췄다면 4번 보내도 4번 실패하고, 아픈 api에 요청만 늘어납니다. 그래서 횟수를 작게 둡니다

<details><summary><b>이렇게 나오면?</b> — 자주 나는 오류와 해결 (눌러서 펼치기)</summary>

| 화면 | 원인 | 해결 |
|---|---|---|
| 여전히 절반쯤 503 | 적용 직후, 또는 `retries`를 `api-abort.yaml`에 넣음 | 5초 뒤 다시. 재시도는 `web` 규칙에(확인 문제 2) |
| `http retry policy configured when attempts are set to 0` | `attempts: 0`에 `retryOn`을 같이 씀 | 끌 때는 `retries: {attempts: 0}`만 |

</details>

## 끝났는지 확인
- ☐ 지연 주입 뒤 규칙 없이 `200 2.0…s` → 타임아웃 뒤 `504 1.0…s`, 홈은 `200`
- ☐ 실패 주입 50% 뒤 100번 중 503이 절반쯤, 본문 `fault filter abort`
- ☐ 재시도 3회 뒤 503이 한 자리 수
