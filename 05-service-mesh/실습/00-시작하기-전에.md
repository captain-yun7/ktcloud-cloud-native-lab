# 시작하기 전에

접속·붙여넣기·YAML 쓰기·PORTS 탭은 Kubernetes 과목과 같습니다. 자세한 설명은 [Kubernetes 실습 문서의 시작하기 전에](../../02-kubernetes/실습/00-시작하기-전에.md)에 있습니다.

## 1. 접속과 명령 치는 곳
- 접속: `ssh ktc-sNN` — [접속 안내](../../00-접속-안내.md)
- 모든 명령은 **VM 터미널**에서 칩니다. `kubectl`·`linkerd`·`istioctl` 모두 VM에서 실행해 클러스터에 명령을 보냅니다

## 2. 이 과목부터 노드 3개 클러스터
- 실습 1에서 클러스터를 **노드 3개(full 프로파일)** 로 다시 만듭니다. 메시와 모니터링을 올려도 자리가 모자라 `Pending`이 나지 않게 하려는 것입니다
- 다시 만들면 **앞 과목에서 클러스터에 올린 것은 모두 지워집니다.** VM의 파일(`~/ktcloud-cloud-native-lab`, `~/ob` 등)과 VM 도커의 이미지는 그대로입니다
- 이 클러스터는 다음 과목(모니터링)까지 계속 씁니다. 막혔다고 클러스터부터 다시 만들지 마세요 — Linkerd·Istio·쇼핑몰을 처음부터 다시 올려야 합니다

## 3. YAML 파일 쓰기
- 이 과목의 YAML은 `~/mesh` 폴더에 둡니다. `nano 파일`로 열어 붙여 넣습니다(저장 Ctrl+O → Enter, 나가기 Ctrl+X)
- 들여쓰기는 스페이스 2칸, 탭 금지

## 4. 출력이 문서와 조금 달라도 되는 것
- 파드 이름 끝의 글자, IP, 시간(초), 요청 수 같은 숫자는 사람마다 다릅니다
- **비율**(90:10 등)은 대략 맞으면 됩니다. 100번이면 v2가 5~15번 정도는 정상 범위입니다. 요청마다 주사위를 굴리듯 고르기 때문입니다
- `kubectl exec …` 결과 위에 `Defaulted container "…" out of: …` 한 줄이 붙을 수 있습니다. 파드에 컨테이너가 여럿(앱 + 프록시)이라 첫 번째 것을 골랐다는 안내입니다. 문서의 명령은 `-c 이름`으로 컨테이너를 정해 이 줄이 대부분 나오지 않습니다

## 5. 막히면 — 질문하는 법
- 에러 첫 줄을 **글자로** 복사해 Discord에 올립니다. 한 일 / 기대한 것 / 실제 화면 / 해 본 것

## 이 문서에 나오는 말

| 말 | 쉬운 뜻 |
|---|---|
| 서비스 메시 | 서비스끼리 주고받는 요청을 앱 밖에서 한꺼번에 다루는 장치. 파드마다 프록시를 붙여 암호화·지표·재시도 등을 코드 수정 없이 붙임 |
| 프록시 | 요청을 대신 받아 넘겨 주는 프로그램. 메시에서는 파드마다 하나씩 붙음 (Linkerd는 `linkerd-proxy`, Istio는 `istio-proxy` = Envoy) |
| 사이드카 | 앱 컨테이너 옆에 같이 붙어 도는 보조 컨테이너. 메시의 프록시가 사이드카. 그래서 READY가 `1/1` → `2/2` |
| 주입 | 파드가 만들어질 때 사이드카를 자동으로 끼워 넣는 것. 이미 떠 있는 파드에는 안 들어가서 다시 만들어야 함 |
| 제어 영역 (control plane) | 프록시들에게 설정·인증서를 나눠 주는 곳. Linkerd는 `linkerd` 네임스페이스 파드 3개, Istio는 `istiod` 하나 |
| 데이터 영역 (data plane) | 실제로 요청이 지나가는 프록시들 |
| mTLS | 양쪽 프록시가 서로 인증서를 확인하고 암호화해서 주고받는 것. 앱은 평문으로 보내고 받음 |
| 신분 (identity) | 인증서에 적힌 "나는 누구다". 메시는 파드의 **서비스 계정** 이름으로 정함 (예: `api.todo` = 네임스페이스 todo의 계정 api) |
| 골든 지표 | 서비스 상태를 보는 기본 숫자 — 성공률(SUCCESS), 초당 요청 수(RPS), 지연(p50·p95·p99) |
| p95 | 요청 100개를 빠른 순으로 줄 세웠을 때 95번째의 시간. "느린 쪽은 얼마나 느린가" |
| 카나리 배포 | 새 버전을 일부 요청(예: 10%)에만 먼저 보내 보는 것 |
| VirtualService | Istio 규칙 — 요청을 어느 묶음으로 보낼지(비율·헤더), 타임아웃·재시도·장애 주입 |
| DestinationRule | Istio 규칙 — 목적지 파드를 라벨로 묶음(subset)으로 나눔 |
| 타임아웃 · 재시도 | 정한 시간 안에 답이 없으면 끊기 · 실패한 요청을 다시 보내기 |
| 장애 주입 | 프록시가 일부러 늦추거나 실패를 돌려줘서, 앱이 견디는지 시험하는 것 |
| Kiali | Istio 프록시 지표로 서비스 관계도를 그려 주는 화면 |
